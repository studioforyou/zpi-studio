## Own make-up credits

`GET /api/v1/me/profiles/{profileId}/makeup-credits` lists unused make-up credits for the active account's own participant profile or a child it currently represents. It returns a standard page (`page`, default 0; `size`, default 20, maximum 100). `totalItems` is the full available count; items are ordered by expiry and ID, with the source pass's saved product name, `grantedAt` and exact UTC `expiresAt`.

Only `AVAILABLE` credits with a future expiry and no usage markers are included. An expired source pass does not invalidate an otherwise valid credit. This read does not grant credits or determine eligibility for a particular class. It uses the existing `makeup_credit` and `customer_pass` tables without a schema migration. Dev/stage seed 09 repairs the original unused Monika example's misleading Open-pass link, using a separate expired four-entry Pole Dance pass with a make-up policy. It preserves the credit's status and dates and leaves used or reassigned credits alone. Katarzyna also has used and expired examples.

## Notifications

`communication` sends push notifications to the mobile app and keeps every notification in the recipient's in-app inbox (#142).

- **Types.** Each type is a `notification_type` row loaded by a migration and a `NotificationType` constant, with the `{{name}}` placeholders its template can use. Placeholder names are Polish (e.g. `{{zajęcia}}`, `{{ile przed}}`) because the studio administrator writes the templates; the panel inserts them with buttons and shows a preview. The administrator configures every type in the web panel (`GET`, `PATCH /api/v1/notification-types/{code}`): on/off, the push title and text, and for a timed type 1 to 5 reminder times (`notification_lead_time`, 5 minutes to 14 days before the start). A new type must appear there; its issue only adds the source of the notification and its default content.
- **Recipients.** A notification goes to an account. A child's notification goes to every active guardian and names the child (`subject_customer_id`). A guardian sees the participant's first name in every title, its own notifications too, e.g. `Monika: …` and `Zosia: …`. For an account with several roles (client and trainer) the title starts with the role it concerns, e.g. `Klient · Kuba: …`, and `recipient_role` lets the inbox show only the active role's notifications.
- **Devices.** The app registers its FCM token after sign-in (`POST /api/v1/me/devices`, a token moves to the account that registered it last) and removes it before sign-out (`DELETE /api/v1/me/devices/{token}`). Tokens FCM reports as invalid are revoked when a push fails.
- **Inbox.** `GET /api/v1/me/notifications?role=CLIENT`, `GET .../unread-count`, `POST .../{id}/read` and `POST .../read-all`.
- **Sending.** `PushSender` has two implementations, chosen by `PUSH_PROVIDER`: `LOG` (default, local) only logs, `FCM` sends through the FCM HTTP v1 API with the Firebase Admin SDK and Application Default Credentials. Every attempt is a `notification_delivery` row (`SENT`, `FAILED`, `TOKEN_INVALID`, `NO_DEVICE`). `notification.dedup_key` makes each notification unique, so a job or event that runs twice sends nothing twice.

### Timed notifications: the notification job

Cloud Run scales to zero and has no CPU between requests, so the backend does not run timers in production. Cloud Scheduler calls `POST /internal/jobs/notifications/run` every 5 minutes (see `infrastructure/`) with a Google-signed OIDC token. `/internal/**` has its own security chain: it accepts only a token with issuer `https://accounts.google.com`, audience `JOBS_OIDC_AUDIENCE` and the verified e-mail `JOBS_OIDC_SERVICE_ACCOUNT`, and rejects everything while either is unset. Firebase user tokens are not accepted there.

One run:

1. sends class reminders that are due: for every active reservation of a class that is not cancelled, each reminder time from `start - lead time` for 30 minutes, if the reservation already existed then;
2. sends reminders about expiring passes (`PASS_EXPIRING`, #146): each reminder time counts back from 9:00 on the last day of the pass, for 30 minutes, if the pass already existed then; passes with no entries left and participants who already hold a following pass are skipped;
3. retries pushes that failed in the last 12 hours (after 2 minutes, at most 3 failed attempts);
4. re-delivers domain events whose listener has not finished (see below).

Locally, with Docker Compose, `JOBS_LOCAL_SCHEDULER_ENABLED=true` runs the same job inside the backend every 5 minutes instead.

### Notifications sent right after an event

A module that has something to notify about publishes a domain event in its own transaction; `communication` listens and sends right away:

```java
@Async
@TransactionalEventListener
void on(ClassCancelled event) {
    notifications.notifyNow(List.of(new NotificationRequest(...)));
}
```

Spring Modulith's event publication registry (`event_publication`) stores the event in the same transaction as the business change. The listener runs after the commit, on another thread, so a failing push never fails the user's request. A listener that fails or does not finish stays in the registry, and the notification job delivers it again after 2 minutes; the dedup key keeps the notification single. Completed publications are deleted (`spring.modulith.events.completion-mode: delete`).

## Tests

Requires JDK 21. From `backend/`, run only the module architecture test without a Spring context, database, or Docker:

```powershell
.\mvnw.cmd -B '-Dtest=ModuleArchitectureTest' test
```

Run the full backend verification with a running Docker engine. Integration tests use separate, disposable PostgreSQL databases managed by Testcontainers:

```powershell
.\mvnw.cmd -B clean verify
```

On Linux or macOS, use `./mvnw` instead of `.\mvnw.cmd`. The existing Backend CI runs `./mvnw -B verify`, including the architecture test, and checks the Docker image build.

## Application modules

Spring Modulith 2.1.1 uses default module detection: direct subpackages of `studioforyou.pl.backend`, the package containing `BackendApplication`, are modules. All 18 modules have a `package-info.java` declaration with `@ApplicationModule` and a short responsibility description:

- `identity`, `customer`, `staff`, `offering`, `trainings`, `scheduling`, `booking`, `membership`, `documents`, `communication`, `payments`, `reporting`, `integrations`, `configuration`, `files`, `audit`, `shared`, and `system`.

Annotated package declarations are sufficient for detection, including modules without implementation classes. Group and personal training share `trainings`. The declarations establish module boundaries; future business functionality is not implemented by this skeleton.

Before implementing a backend use case or changing persistence, read [Backend modules](https://github.com/studioforyou/zpi-studio/wiki/Backend-modules) and its [instructions for using and maintaining the map](https://github.com/studioforyou/zpi-studio/wiki/Backend-modules#5-how-to-use-and-maintain-this-map). It is the working map of module responsibilities, table ownership, and expected collaboration for the full functional scope. Add concrete operations, data types, events, and dependencies with the use case that requires them; document detailed contracts and business rules on the relevant module or use-case Wiki pages.

When responsibilities, table ownership, or collaboration change, update the map as part of the same work, adjust the affected code and architecture checks where applicable, and link the relevant Wiki pages or revisions in the pull request. Include any affected contract and rule documentation in that same work. Each module accesses only its own tables; other modules use its public operations or events.

The existing `configuration`, `shared`, and `system` implementations remain in place. The `system.internal` package contains `PingController`, preserving `GET /api/ping` and its existing response; `configuration` still provides `GET /api/v1/studio`. `offering` provides the pass product catalogue (`/api/v1/pass-products`, changed only by `ADMIN` accounts) and the service catalogue (`/api/v1/service-types`): active accounts can read service definitions, while administrators create and edit their participation rules and activate or deactivate them. Existing pass and room references remain unchanged. `customer` provides a search of active participants for administrators (`GET /api/v1/customers`). It also lists the studio's active trainers by name for every active account (`GET /api/v1/trainers`, only `staffId` and `displayName`), e.g. for the trainer filter of the class offer. `membership` lets administrators assign passes to participants and list them (`/api/v1/customers/{customerId}/passes`); it reads variant terms through `offering`'s `PassVariantLookup`, participants through `customer`'s `CustomerProfiles`, and today's date and the currency through `configuration`'s `StudioSettings`.

The `staff` module provides read and update operations for the signed-in trainer's personal details through `GET` and `PATCH /api/v1/me/staff-profile`, available to active accounts with the `TRAINER` role.

Administrators correct a participant's finite pass balance with `POST /api/v1/customers/{customerId}/passes/{passId}/correct-entries` (#83), sending a nonzero integer `entriesDelta`, the current pass `version`, and an optional `reason` of up to 500 characters. The response is the updated pass. Corrections retain the original entry total, status and validity, and append `CORRECTION` to the existing `pass_ledger` with the administrator, time, signed change and reason. No schema migration is needed. The pass row is locked in the same way as booking accounting; a stale version returns `409 VERSION_CONFLICT`. Unlimited passes, negative resulting balances and balances exceeding 32767 (including still-returnable allocations) return `400 VALIDATION_FAILED`. Historical and suspended finite passes can be corrected without making them usable for booking again.

`scheduling` manages rooms and the service types allowed in them under `/api/v1/resources` (#133), for `ADMIN` accounts only; it reads service types through `offering`'s `ServiceTypes`.

Service definitions include booking and cancellation settings managed through `configuration`'s public `BookingPolicies` contract. `GET /api/v1/service-types/booking-defaults` returns studio defaults; a service returns its explicit overrides and effective settings. Saving a definition and its rules is atomic. Policy changes create new versions in `booking_policy`, preserving existing references; this use case stores configuration without executing booking or cancellation workflows.

The trainer profile controller and HTTP DTOs live in `staff.internal`, alongside the module's persistence implementation. They obtain the active account ID through `shared.api.AccountAuthentication`, implemented by the verified identity token. The existing `identity` session lookup still uses the public `StaffProfiles` contract, without introducing a reverse `staff` dependency on `identity`.

`scheduling` also holds the studio's schedule (#130, #131): one-off and recurring events with their staff and rooms (`/api/v1/schedule-events`, `/api/v1/recurrence-series`), for `ADMIN` accounts only. It reads staff members, their qualifications, leave and working hours through `staff`'s `StaffProfiles` and `StaffAvailability`, and the studio's time zone through `configuration`'s `StudioSettings`. `staff` lists staff members (`GET /api/v1/staff`) and `trainings` lists training groups (`GET /api/v1/training-groups`) for administrators.

`booking` provides the client group-class offer, own upcoming reservations, booking and cancellation under `/api/v1/me/profiles/{profileId}` (#87, #88, #89, #118). The same profile scope lists the training history (#97, `GET .../training-history`): booked events that already started, one entry per event with its outcome (`PRESENT`, `ABSENT`, `UNMARKED`, `CANCELLED`, `LATE_CANCELLED` or `CLASS_CANCELLED`); booking passes only its own reservations' event IDs to `scheduling.GroupClassSchedule.findStartingBetween`, which reads them regardless of kind or visibility. It authorizes own/child profiles through `customer`, reads public occurrences and acquires their locks through `scheduling.GroupClassSchedule`, checks service/age rules through `offering` and required acceptances through `documents.DocumentRequirements`, resolves scoped terms through `configuration.BookingPolicies`, and allocates or returns pass entries through `membership.BookingEntitlements`. Each owner reads only its own tables; occurrence, reservation and pass accounting commit in one transaction.

A full class has a waiting list (#94). The class projection's `waitlist` tells whether the profile can join (`allowed`, `reason`), how many participants wait (`waitingCount`) and the profile's own entry with its 1-based `position` and `promotionBlockedReason`. `POST .../group-classes/{eventId}/waitlist-entries` with a chosen `customerPassId` joins it (`201` with `Location`, `200` with the existing entry on a retry) and charges nothing; `GET`/`POST .../waitlist-entries/{entryId}` (`/cancel`) read and leave it. Joining needs what booking needs except a free place, plus `waitlistEnabled` in the effective policy: otherwise `ALREADY_RESERVED` or `CLASS_NOT_FULL` (`409`), or `WAITLIST_DISABLED`, the booking reasons and `PASS_NOT_USABLE` (`422`). The queue is ordered by join time (taken under the occurrence lock) and ID; the booking-owned `waitlist_entry` table gets `customer_pass_id` in V10, without new module dependencies.

When a participant cancels, the same transaction gives each freed place to the first waiting participant who could book it at that moment: the joining account still acts for them, the booking window is open, the service, age and document rules hold, and the chosen pass or, when it can no longer be used, another eligible pass funds it. The reservation is made like a booking, with `source = 'WAITLIST'` and `booked_by` the joining account; the entry becomes `PROMOTED`. Others are skipped and keep their place, and `promotionBlockedReason` shows why. Booking a free place directly while waiting marks the entry `BOOKED`. The cancellation releases one participant's pass and the promotion reserves another's, so all pass operations of that transaction run in ascending pass ID order (lock order: occurrence, reservations, waiting-list entries, passes); a pass that changed after the promotion check refuses the whole cancellation with `409 VERSION_CONFLICT`, unchanged. `waitlistEnabled` controls joining only.

With a positive `waitlistConfirmMinutes` in the effective policy (the panel's "Wymagaj potwierdzenia zwolnionego miejsca"), a freed place is not booked at once: it is held for that first eligible participant as an `OFFERED` entry until `offerExpiresAt` (the confirmation time, at most until booking closes), and nobody else can book it (`availablePlaces` leaves it out). `POST .../waitlist-entries/{entryId}/confirm` books it under the booking rules of that moment, with only the participant's own pass locked (`200` with the `PROMOTED` entry and its `reservationId`; a repeat returns it; `409 WAITLIST_OFFER_EXPIRED`, `422 WAITLIST_ENTRY_NOT_OFFERED` or a booking reason). Declining with `/cancel`, or not confirming in time (`EXPIRED`), passes the place to the next eligible participant. Every booking, join and cancellation of the class first closes its expired offers under the occurrence lock; a scheduled task (`booking.waitlist.offer-expiry.interval`, default one minute; `booking.waitlist.offer-expiry.enabled=false` turns it off) does it for classes nobody touches. The projection's `waitlist.confirmationMinutes` tells clients which mode applies. Notifying the participant of a place or an offer is #145.

Trainers see the details and participants of the events they run or assist (#103). `scheduling` returns one of the trainer's own events (`GET /api/v1/me/schedule-events/{eventId}`), and `booking` lists its participants with an active reservation (`GET /api/v1/me/schedule-events/{eventId}/participants`): names, adult or child, date of birth and booking time, without contact details. `booking` gets the trainer's staff profile through `staff`'s `StaffProfiles`, checks the assignment through `scheduling`'s `ScheduledEvents` and reads the participants through `customer`'s `CustomerProfiles`. Another trainer's event, a block or an unknown event all answer `404`.

Trainers record the attendance of the events they run or assist (#102), group classes and personal sessions alike: `GET`/`PATCH /api/v1/me/schedule-events/{eventId}/attendance` reads the sheet and records `PRESENT` or `ABSENT` for several participants at once, and `POST /api/v1/me/schedule-events/{eventId}/complete` marks the event as held: participants still unmarked become `PRESENT`, a personal session gets `trainer_confirmed_at`, and `scheduling.ScheduledEvents.markCompleted` sets the event `COMPLETED`. Trainers can do this from the event's start until 12 hours after its end (`ATTENDANCE_NOT_OPEN`, `ATTENDANCE_CLOSED`, `EVENT_CANCELLED` otherwise). Administrators read every event's attendance with its history (`GET /api/v1/schedule-events/{eventId}/attendance`) and correct it at any time after the start (#111, `POST /api/v1/schedule-events/{eventId}/reservations/{reservationId}/correct-attendance` with `attendance`, an optional `reason` of up to 500 characters and the reservation's `version`; a stale one returns `409 VERSION_CONFLICT`). The first recorded attendance, present or absent alike, settles the pass entry allocated at booking as used through `membership.BookingEntitlements.consume`, so later changes never touch the pass. Every change is appended to `audit_log` (`ATTENDANCE_MARKED`, `ATTENDANCE_DEFAULTED`, `ATTENDANCE_CORRECTED`) with its author and reason, and read back through `audit.AuditLog.history`; the reservation keeps only the current value. No schema migration is needed. Locks follow the booking order: event, reservations, then passes in id order.

Administrators book and cancel group-class places on behalf of participants (#110), e.g. after a phone call or at the desk, for public and private classes (`scheduling`'s `GroupClassSchedule` now also finds and locks private classes). `GET /api/v1/schedule-events/{eventId}/reservations` lists the class's active places with who booked them (`source`, `bookedBy`), the pass name (through `membership`'s `TraineePasses.funding`), the reason and overridden issues, and the cancellation terms; `GET .../booking-options?customerId=` tells whether the participant can be booked, their eligible passes and the `issues` to confirm. `POST .../reservations` (`customerId`, `customerPassId`, `acceptedIssues`, optional `reason`) books the place with `source = 'STAFF'` until the class starts, whatever the booking window. A full class (`CLASS_FULL`) and each unmet requirement (`SERVICE_TYPE_UNAVAILABLE`, `AGE_RESTRICTION`, `REQUIRED_DOCUMENTS_MISSING`, `NO_ELIGIBLE_PASS`) has to be listed in `acceptedIssues`, otherwise `409 BOOKING_OVERRIDE_REQUIRED` returns the current `issues`. A participant with an eligible pass is charged from the chosen one; without one, `NO_ELIGIBLE_PASS` books the place without a pass entry. The cancellation terms are stored as for a participant's own booking, so the participant sees the place among their reservations (a private class too) and can cancel it in the app on those terms; a place without a pass has no entry consequence (`cancellation.entryReturned` and `expectedEntryReturned` are `null`). A waiting participant leaves the waiting list (`BOOKED`). `POST .../reservations/{reservationId}/cancel` (`expectedVersion`, `returnEntry`, optional `reason`) cancels the place until the class starts, also when the participant could not; the administrator decides whether the entry is returned (`cancellation.suggestedEntryReturned` is what the stored terms give), and the freed place goes to the waiting list in the same transaction. Bookings and cancellations are appended to `audit_log` (`RESERVATION_BOOKED_BY_STAFF`, `RESERVATION_CANCELLED_BY_STAFF`) with the reason. Only `ADMIN` accounts; no schema migration.

Trainers book participants on the group classes they run or assist (#106), e.g. a person who asked them to join outside the app's own booking, on the rules of the participant's own booking and without any override: `GET /api/v1/me/schedule-events/{eventId}/booking-options?customerId=` returns `allowed`, the first broken rule as `reason` (`ALREADY_RESERVED`, `CUSTOMER_NOT_ACTIVE`, `EVENT_NOT_BOOKABLE`, `BOOKING_NOT_OPEN`, `BOOKING_CLOSED`, `CLASS_FULL`, `SERVICE_TYPE_UNAVAILABLE`, `AGE_RESTRICTION`, `REQUIRED_DOCUMENTS_MISSING`, `NO_ELIGIBLE_PASS`), the waiting-list status and the eligible passes; `POST /api/v1/me/schedule-events/{eventId}/reservations` (`customerId`, required `customerPassId`, optional `reason`) rejects with the same codes as self-service booking and otherwise books through `StaffBookingService` with `source = 'STAFF'`, the trainer as `booked_by` (so `bookedBy` shows their name) and `RESERVATION_BOOKED_BY_STAFF` in `audit_log`. Another trainer's class, a personal session and an account without a staff profile return `404`, as in the trainer's other event endpoints (`scheduling.ScheduledEvents.isAssigned`). Cancelling a place stays with administrators. No schema migration.

Trainers keep a card for each participant they currently work with (#99), owned by `trainings`: `GET`/`PATCH /api/v1/me/trainees/{customerId}/card` reads and changes the goals and sport experience (omitted fields stay unchanged, blank text clears a field, at most 2000 characters each). A participant has one card, shared by all of their current trainers, so a change sends the card's `version` (0 for a card nobody has filled in yet) and a stale one returns `409 VERSION_CONFLICT`. The card carries the participant's health notes only when `healthAccess` is `GRANTED`: the trainer needs the `CUSTOMER_HEALTH_READ` permission and the participant's consent on the trainer's own assignment (`staff_assignment.can_view_health`); otherwise it is `NO_PERMISSION` or `NOT_SHARED` and `healthNotes` is `null`, so nothing tells whether hidden notes exist. With access a trainer adds a note (`POST .../health-notes` with `kind` `INJURY`, `CONDITION`, `CONTRAINDICATION` or `OTHER` and a `description` of up to 1000 characters) and archives one that no longer applies (`POST .../health-notes/{noteId}/archive`, a repeat returns the archived note); notes are never edited or deleted, and an archived note shows who archived it and when. Without access these return `403` with `ACCESS_DENIED` or `HEALTH_DATA_NOT_SHARED`. Like the trainee's profile, the card is not found (`404`) for another trainer's participant, after the cooperation ends and for an inactive participant. `trainings` reads the assignment and its consent through `customer`'s `StaffAssignments.findActive`, the trainer's staff profile through `staff`'s `StaffProfiles`, and the authors' names through `displayNamesByAccount` of both modules. V15 adds `trainee_card.version` and `health_note.archived_by`. How participants give or withdraw the consent is a separate story; until then it comes from the database.

`reporting` counts active and new customers in a period of studio dates for administrators (#163, `GET /api/v1/reports/customer-activity`), together with the period of the same length right before it. It owns no tables and assembles the counts through public read operations: `membership`'s `PassHolders` (participants with a valid pass), `scheduling`'s `ScheduledEvents` (events that were not cancelled) and `booking`'s `Participations` (participants with an active reservation) give the active customers; `identity`'s `AccountStatistics` (activated client accounts) and `customer`'s `CustomerProfiles` (profiles without an account) give the new ones. Administrators create other administrators' accounts directly, without an invitation e-mail (`POST /api/v1/admin-accounts`): the backend generates a strong password and returns it only in that response, so the creating administrator can pass it on privately (the new administrator changes it in the panel's account menu, or with the password reset on the login page, both handled by Firebase). The account is `ACTIVE` at once, gets a staff profile, and its Firebase user is only ever created, never taken over, so an e-mail already used in Firebase returns `409 ACCOUNT_ALREADY_EXISTS`.

`reporting` also reports attendance and occupancy of group classes (#164, `GET /api/v1/reports/class-attendance`) and no-shows and cancellations (#166, `GET /api/v1/reports/booking-outcomes`) for administrators. Both take the same query (`ReportQuery`): a period of studio dates validated as for #163, and filters of the events, each repeatable or comma separated: `kind` (`CLASS`, `WORKSHOP`, `PERSONAL_TRAINING`; by default the first two, and attendance takes only those), `serviceTypeId`, `staffId` (who runs or assists the event), `trainingGroupId` and `resourceId` (a room of the event). An event matches when it has one of the values of every filter given. Both count only events that already started and were not cancelled, so a period reaching into the future ends now. A participant attended unless marked absent: an unmarked place counts as present, as when the trainer completes the event, and is also counted in `unmarked`. Occupancy is `placesBooked / places` over the events with a limit of places; a recurring series is one class in the per-class rows. Cancellations are `IN_TIME` or `LATE` as booking recorded them, grouped by how long before the start they came (0-2, 2-6, 6-12, 12-24, 24-48 and 48+ hours); each service shows its effective cancellation rules now. The reports own no tables: `scheduling`'s `ScheduledEvents.findNotCancelledStartingBetween` gives the events matching an `EventFilter` (kind, service, fixed group, series, capacity; staff and rooms through its own `event_staff` and `event_resource`), `booking`'s `Participations.countOutcomes` and `findCancellations` what became of their places and waiting lists, `offering`'s `ServiceTypes` the services and their rules, and `trainings`' `TrainingGroups` the group names. No schema migration.

Modules retain their default closed boundaries. Public types in a module's base package form its default API. Subpackages are internal unless explicitly exposed with `@NamedInterface`. The `shared.api` package declares `@NamedInterface("api")`, exposing the existing common API types to `configuration` without opening the whole `shared` module.

`ModuleArchitectureTest` checks that `ApplicationModules.of(BackendApplication.class)` discovers exactly the 18 modules listed above, including those containing only package declarations, and calls `verify()` to check module boundaries and dependency cycles. It runs without starting a Spring context, database, or Docker.
